# ADR-006：答案采用「当前值 upsert + 修订流水 append-only」双表

**状态**：已接受　**日期**：2026-11-12

## 背景

两个需求彼此拉扯：

1. **可靠**：答题必须能恢复（刷新、崩溃、换设备都不丢），且要能证明「某人在某时刻答了什么」。
2. **性能**：单场 1000 人作答，答案保存是全系统最高频的写路径（峰值约 1000 RPS）。

单一表做不到两者兼得：只存当前值，则无法追溯作答过程（考试公平性无法审计）；
只存流水，则每次读取当前答案都要扫全量流水。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 单表存流水，读时取最新 | 审计完整 | 读放大严重，1000 题 × 多次保存 → 恢复时要扫上万行 |
| 单表存当前值 | 简单、读快 | 无作答过程留痕，无法支撑事后认定与申诉举证 |
| 单表 append-only + 物化视图 | 审计完整 | 运维复杂，视图刷新延迟影响恢复速度 |
| **双表：当前值 + 修订流水** | 读快 + 可审计 | 多一张表与一次额外写入 |

## 决策

采用双表：

- `delivery.answer` —— 当前值，`(attempt_id, question_id)` 唯一，走 upsert。恢复会话时一次查询读全。
- `app.answer_revision` —— 修订流水，追加式，`(attempt_id, client_seq)` 唯一保证幂等。
  数据库层已 `REVOKE UPDATE, DELETE`。

`app` schema 单独隔离，只授予 `SELECT, INSERT` 权限。

## 代价与后果

- 每次保存产生两处写入。按峰值 1000 RPS、每批 50 条计算，实际约 40 批次/秒，
  即约 40 次 answer upsert + 40 次 revision 批量插入，压力可接受。
- 追加式表的写入不可回滚，故对账作业（每日 + 考试期间每 10 分钟）必须存在，
  发现差异时以 `answer_revision` 为准重建 `delivery.answer`。
- 两个 schema 的权限分离需要在部署时由 `db-grants` 一次性任务执行（见 `deploy/db/02-grant-app-role.sql`）。
