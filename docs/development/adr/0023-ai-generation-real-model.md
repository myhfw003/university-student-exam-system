# ADR-023：AI 生成试题接入真实大模型（OpenAI 兼容协议，供应商与模型可切换）

**状态**：已接受　**日期**：2026-11-26

## 背景

ADR-010 定了「导入走真实实现，**不预留空的 AI 生成接口**」——那时既没有模型，
也没有确定的供应商，留个空壳只会让人以为功能已经有了。

现在情况变了：

- MiniMax 等厂商提供了稳定的 **OpenAI 兼容**接口（`POST {base}/chat/completions`），
  一份 HTTP 客户端就能接一家，换厂商只是换一份配置；
- 老师对「AI 出题」的需求是实的：出题是内容生产里最费时间的一环；
- 但**模型输出不可信**：它会把选项写成对象映射、把答案键写错、把综合题的步骤分值对不上。
  没有校验的生成功能只会往题库里灌垃圾。

于是要定的不是「要不要接模型」，而是「**接进来的模型产出怎么才算一道题**」。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 只留 Provider 抽象，不接真实模型（ADR-010 的做法） | 诚实，不产生费用 | 功能没有；等下去只会更晚 |
| 每家厂商写一个 SDK 客户端 | 用厂商的最佳实践 | 代码多；换模型还要改代码 |
| **按 OpenAI 兼容协议做一份通用客户端，供应商与模型由配置给出** | 一份实现接多家；换模型不改代码 | 厂商的非标准字段要单独兼容（如 MiniMax 的 `base_resp`） |
| 自建模型输出一套独立的校验规则 | 与导入解耦 | **两套规则必然漂移**：导入认的格式 AI 不认，AI 认的导入不认 |

## 决策

**接真实模型**，且：

1. **协议层**：按 OpenAI 兼容协议实现（`Authorization: Bearer`、
   `choices[0].message.content`）。供应商与模型清单写在配置里
   （`AiGeneration:Providers:<name>`），**换厂商、换模型都不改代码**。
   API Key **只从环境变量来**，配置文件里留空，密钥不入库。
2. **校验层**：模型产出**不另立一套规则**。模型的原文先被容错解析成草稿
   （剥思考段、剥代码块、认对象式选项），再翻译成**导入行**，交给
   `QuestionImportParser`——与文件导入共用同一套校验。组题走同一个
   `QuestionComposer`（判断题固定两个选项、综合题分值与评分步骤都在这里定）。
3. **落库层**：通得过校验的题直接成为**候选题（草稿，`source = generated`）**，
   与导入的产物进同一个队列、同一个发布流程；**通不过的不落库**，逐条说明哪里不合法。
4. **失败要分清**：服务端没配 API Key 是 **422**（配置问题，不是用户的错）；
   上游报错、网络不通是 **502**（上游的问题）。两者都带稳定错误码。
5. **不落独立批次表**：生成历史即候选题本身，加上审计日志里的 `ai.generate` 动作。
   批次表是以后要「回看某次生成」时再加的东西，现在加就是空表。

## 代价与后果

- **模型会出错，而且出错的形状不固定**（今天返回选项对象，明天返回带思考段的数组）。
  容错解析与「逐题给结论」是这条路的成本，不能省。
- **生成结果不可信到能进题库的程度**：所以它进的是候选题队列，要人复核发布，
  不是直接进可用题池。
- **依赖外部服务**：模型服务挂了、限流了、没配 Key，AI 生成这条路就是不通的——
  导入那条路不受影响。公测机（容器网络无 DNS、无出网）上 AI 生成暂时用不了，
  这是环境限制，不是代码问题。
- 收益：AI 出题从「界面上写着但不接入」变成真的能用，且**与导入共用规则**，
  不会出现「导入认的格式 AI 不认」这种漂移。
