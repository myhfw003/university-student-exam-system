# ADR-021：重置密码统一置为系统设定的原始密码

**状态**：已接受　**日期**：2026-11-23

## 背景

管理员重置用户密码这件事，原来的实现是「响应里带一个系统随机生成的初始密码」
（或管理员临时指定一个新密码）。产品定的口径（2026-11-23）是：

> 重置密码的响应中不应该出现初始密码，重置密码会重置为系统设置的指定原始密码。

也就是说，管理员在「系统设置」里配**一个**原始密码，之后重置任意用户密码，
都置成它；密码由管理员自己另行告知用户，接口不参与传递。

顺带解决的另一个问题：原来「新建用户不指定密码」时系统生成一个随机初始密码，
而**响应里并没有这个密码**（新建用户的响应 DTO 里没有密码字段）——
密码生成了却没人知道，那个账号等于建了个空壳。统一到「原始密码」这条路上之后，
这类场景至少有了一个管理员知道的、可交付的凭据。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 响应里带随机初始密码（原来的做法） | 管理员不用记密码，直接转交 | 密码经接口明文传递，与 FR-AUD-02「响应中密码一律脱敏」冲突；随机密码没记下来就丢 |
| 管理员逐个指定新密码 | 每个用户一个独立密码 | 管理员要自己想密码；用户多了就是体力活；与产品定的口径不符 |
| **系统设定一个原始密码，重置一律置成它** | 管理员配一次，之后一键重置；密码不经接口传递；响应里没有任何密码 | 全系统共用一个初始密码；被重置的用户共用同一份哈希（因而共用同一个盐） |

## 决策

**系统设一个原始密码（存哈希），重置密码一律置成它，响应里不带任何密码。**

- 原始密码存进 `system_setting` 表，键 `original_password_hash`，
  值是 **PBKDF2 哈希**（与用户密码同一套参数，ADR-016）：
  明文用完即弃，不落库、不进日志、不回显。
- **只写不回显**：`GET /settings` 只给「有没有配」这一位
  （`originalPasswordConfigured`）；`PUT /settings/original-password`
  的请求体收明文，`DELETE /settings/original-password` 清掉它。
- 重置接口 `POST /users/{id}/reset-password` **不再收密码**，
  也不再回密码：目标值由后端从设置里取。
- **没配就不能重置**：返回 `422` + `errorCode=29005`
  （`OriginalPasswordNotConfiguredException`），不生成任何交付不出去的随机密码。
- 重置后照旧：用户下次登录必须改密、旧令牌立即失效。
- 权限：设置 / 清除原始密码要 `system:configure`（它在「系统设置」这一面上，
  按需求文档 §1 的矩阵只给系统管理员）；重置仍要 `user:write`
  （内容管理员也能重置，重置的目标值由系统管理员配好）。

## 代价与后果

- **所有被重置的用户共用同一份哈希**，因而也共用同一个盐。
  这是「全系统一个初始密码」的必然结果：密码本身是同一个值，
  区分用户靠的是用户各自的账号与后续改密，不靠初始密码。
- **初始密码一旦泄露，影响面是全部用户**——只能靠「用户登录后必须改密」
  这条规则兜底（重置后 `MustChangePassword=true`，
  标记期间只放行改密 / 本人档案 / 登出）。
- **管理员要自己保管这个密码**：系统不再显示它，只能靠管理员另行告知用户。
- 「新建用户不指定密码」的路径**不在本次范围内**：
  它仍然生成随机初始密码，且响应里仍然没有这个密码（那个缺口另行处理）。
- 审计动作码 `settings.update` / `settings.original_password` /
  `settings.original_password_clear` 统一到 `settings.*` 家族：
  两段式（`system.settings.update`）落在 `scripts/check-audit-action-codes.py`
  的校验范围之外，前端审计页显示不出中文名。
