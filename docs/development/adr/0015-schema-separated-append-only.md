# ADR-015：数据库分 Schema，追加式表独立 Schema + 权限收回

**状态**：已接受　**日期**：2026-11-12

## 背景

「记录只追加、不可篡改」如果只靠代码约定，就等于没有约束：任何一次误用
`SaveChanges` 的更新路径、或一个拿到应用账号的脚本，都能改掉审计流水与答案修订流水。
考试类系统的可信度建立在「事后能证明记录没被改过」上，这个保证必须落在数据库权限上。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|
| 单 schema + 触发器拦截 UPDATE/DELETE | 触发器拦一次 | 触发器容易被误关；难排查；备份恢复时也触发 |
| **按用途分 schema，追加式表单独一个并收回写权限** | 权限即事实：应用账号根本改不了 | 部署要跑一次授权脚本 |
| 只靠代码约定 | 零部署成本 | 约束形同虚设 |

## 决策

数据库按用途分 schema：`iam`、`catalog`、`authoring`、`delivery`、`app`、`grading`、
`learning`、`analytics`、`outbox`、`audit`。

追加式表单独放：

- `app.answer_revision` —— 答案修订流水。
- `audit.audit_log` —— 审计日志。

应用账号 `exam_app` 在这两个 schema 上**只有 `SELECT` 与 `INSERT`，没有 `UPDATE` 与 `DELETE`**，
由部署时的 `db-grants` 一次性任务执行（`deploy/db/02-grant-app-role.sql`）。

## 代价与后果

- 追加式表不能改也不能删：写错了只能追加一条更正记录（这正是审计要的语义）。
- 授权要在每次新增表后重跑（脚本已做成幂等的 `GRANT`/`REVOKE`）。
- 收益：即使应用代码里有 bug，也改不动已经落库的证据。
- 部署顺序有依赖：迁移 → 授权，应用账号在授权之前不能访问新表。
