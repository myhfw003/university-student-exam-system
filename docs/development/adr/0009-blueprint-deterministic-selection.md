# ADR-009：组卷采用规则引擎 + 确定性种子，池不足时报错不降级

**状态**：已接受　**日期**：2026-11-12

## 背景

组卷有两种极端做法：完全手工挑题（老师累，且难保证覆盖度）与纯随机抽题（同一份规则两次
生成的结果不一样，事后无法解释「为什么是这道题」）。学校场景需要中间路线：按规则抽，
但可复现、可解释。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯手工挑题 | 最可控 | 题量一大不可行 |
| 纯随机抽题 | 简单 | 不可复现，覆盖度不可控 |
| **规则 + 确定性种子** | 可复现、可解释 | 实现复杂度高于随机 |
| 规则 + 池不足时静默降级 | 总是能出卷 | 悄悄违反老师设的规则——比报错更糟 |

## 决策

`Blueprint`（组卷方案）描述规则：按题型 / 知识点 / 能力 / 难度各要多少题、总分多少。
执行抽题时用**确定性种子**（方案自带 seed），同一方案 + 同一题库状态 → 同一份卷子。

题池不足时**不降级**：返回 422 并逐条列出缺口（缺哪种维度、缺几道、可用候选有多少），
让老师去补题库或改规则，而不是给他一份悄悄缩水、覆盖度不达标的卷子。

## 代价与后果

- 抽题算法本身是业务代码（`Application/Authoring`），必须进单元测试。
- 「确定性」的前提是题库状态不变：题库变了，同一方案重抽结果会变——这是对的，
  因为卷面本来就该跟题库走。
- 缺口报告是给老师看的，必须具体到「知识点 X 缺 3 道」，否则用户还得自己算。
