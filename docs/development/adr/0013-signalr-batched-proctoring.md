# ADR-013：监考采用 SignalR + 2 秒批量聚合推送

**状态**：已接受　**日期**：2026-11-12

## 背景

监考大屏要同时看到 1000 名考生的在线状态、切屏次数、断线次数与当前作答进度。
这些数据每秒都在变。如果每次变化都推给前端，1000 人 × 每秒数次 = 每秒数千条消息，
浏览器会被淹没，而且大部分变化人眼根本看不见。

## 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 前端轮询 REST | 实现最简单 | 延迟高；每秒轮询 1000 人的状态会把数据库打穿 |
| WebSocket 逐条推送 | 延迟最低 | 消息量爆炸，客户端要做高频渲染 |
| **SignalR + 2 秒批量聚合** | 消息量降两个数量级 | 最多 2 秒延迟（对监考足够） |

## 决策

- 服务端 `ProctoringBroadcaster` 每 2 秒聚合一次，把同一场次的考生状态合成一份快照推送。
- 推送走 SignalR 的 `ProctoringHub`，按场次分组（`exam:{id}`）。
- 多实例部署时靠 Redis Backplane 广播，任一实例都能把消息送到连在其他实例上的监考端。
- 初始快照走 REST（`GET /api/v1/exam-sessions/{id}/monitoring`）：实时通道断线重连后，
  客户端用它补齐断线期间错过的那一段。

## 代价与后果

- 监考看到的状态最多滞后 2 秒——对「考生是否在答题」这类判断足够。
- 断线重连要额外调一次 REST 拿初始快照（已在设计契约里写明）。
- 消息量从「每秒数千条」降到「每秒数百条聚合快照」，浏览器端渲染压力可控。
