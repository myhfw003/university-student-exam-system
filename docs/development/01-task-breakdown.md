# 开发任务拆解

> 关联：`../design/00-overview.md`（决策）、`../design/01-requirements.md`（需求）、`../design/02-architecture.md`（架构）
> 原则：**先基础设施，再逐个模块完成**。每个阶段的产出都必须可运行、可验证、可演示。

---

## 1. 任务编号与规格

| 项 | 规则 |
|---|---|
| 编号 | `T-<阶段>-<序号>`，如 `T-P0-03` |
| 阶段 | P0 基础设施 / P1 身份与标签 / P2 题库与题目 / P3 组卷 / P4 考试组织与作答 / P5 防作弊与监考 / P6 评分与阅卷 / P7 学习与分析 / P8 练习模式 / P9 质量与上线 |
| 每条任务包含 | 目标、依赖、产出物、验收标准 |
| 依赖类型 | `阻塞`（必须先完成）、`建议`（可并行但需协调） |

### 1.1 Definition of Done（完成定义）

一个任务算完成，必须同时满足：

1. 代码通过 `dotnet build`（**警告视为错误**）与前端 `tsc --noEmit`、`eslint`。
2. 对应的单元测试与集成测试存在且通过；新增领域逻辑的分支覆盖率 ≥ 90%。
3. 接口有 OpenAPI 注解；数据库变更有 EF 迁移，且迁移能在空库跑通。
4. 关键操作写审计日志；权限点已在权限矩阵中登记。
5. 错误码已分配，文案为面向用户的中文。
6. 前端改动有组件测试；交互密集的流程有 Playwright 用例。
7. 无 TODO/FIXME 遗留（临时占位须有 issue 编号）。
8. 提交信息符合 `feat(P2): ...` 格式；关联任务号。

**P0 期间发现并修复的缺陷**：

1. 密码策略多项违规时 `ToDictionary` 键重复 → 抛 `ArgumentException` 掩盖了本该抛出的业务异常。
2. 异常中间件未按异常类型区分状态码，参数校验失败返回 422 而非 400。
3. EF 设计时工厂未应用命名约定，迁移与运行期模型不一致（列名 PascalCase 而非 snake_case）。
4. Web 层 `AddControllers()` 漏注册，导致宿主启动即崩溃。
5. `HasDefaultSchema` 未设置，未配置实体落到 `public` schema。
6. Npgsql 10 已移除 `UseServerPreparedStatements` 开关，`Max Auto Prepare` 默认 0（不生成服务端预备语句），与 PgBouncer 事务池天然兼容（设计文档已同步修正）。
7. `global.json` 锁 10.0.401 与容器 SDK 镜像 10.0.400 不兼容，导致镜像构建失败（放宽为 10.0.100 + latestFeature）。
8. Tailwind v4 没有 `--duration-*` 与 `--z-*` 命名空间，正确的是 `--transition-duration-*` 与 `--z-index-*`（前端设计文档已同步修正）。
9. 依赖扫描发现三个真实漏洞并已修复：`Microsoft.AspNetCore.SignalR.StackExchangeRedis` 10.0.14（High，GHSA-wr8v-9x5q-ggcm）、`OpenTelemetry` 1.13.1（Moderate，三条公告）、传递依赖 `SSH.NET` 2023.0.0（High，两条公告）。修复方式：SignalR 适配器升至 10.0.15、OpenTelemetry 全线升至 1.21.0、Testcontainers 升至 4.16.0（连带升级 SSH.NET），并同步把 `Microsoft.Extensions.*` / `Microsoft.AspNetCore.*` 统一到 10.0.15。修复后扫描结果为**未发现漏洞**，72 个测试仍全绿。
10. 设计令牌别名块中 `--ease-out: var(--ease-out)`、`--ease-in: var(--ease-in)` 为**自引用**——在 CSS 中会变成 guaranteed-invalid，且该块未分层、优先级高于 `@theme`，会把正确值覆盖掉，导致缓动曲线失效。已删除这两行（`@theme` 本就提供同名同值定义）。修复后对原型 `tokens.css` 做全量程序化比对：浅色 82/82、深色 37/37 完全一致。
11. 容器 DNS 不可达导致 `docker build` 在 NuGet 还原阶段失败（NU1301）。根因是 BuildKit 的 RUN 步骤不采纳 `--network=host`，且注入的解析器 `100.100.100.100` 在本环境不可达；`docker run --network=host` 正常。绕过方式：`DOCKER_BUILDKIT=0` 经典构建器（`deploy/build.sh` 已提供 `BUILD_LEGACY=1` 开关）。属宿主环境约束，非项目问题。
12. **签名私钥 PEM 在环境变量中换行被转义**，导致 API 容器启动即崩溃（退出码 139）。根因是密钥生成时用 `awk '{printf "%s\n", $0}'` 写入 `.env`，产生的是**字面 `\n` 两字符序列**而非真实换行，`RSA.ImportFromPem` 抛 `No supported key formats were found`。修复：`JwtKeyProvider` 增加三种注入形式并按「挂载文件 → Base64 单行 → 内联 PEM」优先级读取，内联形式额外做 `\n` 归一化；密钥脚本重写为产出 `deploy/secrets/` 下的密钥文件与 Base64 单行文件；`.env` 默认改用 Base64。**根因是密钥注入方式选错，不只是代码缺陷。**
13. **容器健康检查会启动第二个应用实例**。原 `healthcheck.test` 为 `dotnet Exam.Web.dll --health-check`，而 `--health-check` 此前并未实现，等于在探测时拉起完整宿主，与已运行实例争抢 8080 端口。修复：实现 `--health-check` 模式为独立进程探针（只发一个 HTTP 请求，不构建宿主），compose 改为 `["CMD", "dotnet", "Exam.Web.dll", "--health-check", "--probe-url=http://127.0.0.1:8080/health/live"]`。
14. **compose 默认值指向未启动的 PgBouncer**。`DB_HOST` 默认 `pgbouncer`、`DB_PORT` 默认 `6432`，但 PgBouncer 是可选 profile，默认并未启动，导致新环境按 `.env.example` 部署必然连不上库。修复：默认值改为直连 `postgres`/`5432`，启用 profile 时再在 `.env` 里显式改写。
15. **宿主机端口 8088 被其它项目占用**。`docker compose up` 报 `Bind for 0.0.0.0:8088 failed: port is already allocated`，占用方是本机另一个项目的容器。修复：不干预他人容器，改为在 `.env` 里调整 `WEB_PORT`；并在运维手册中写明该报错的处置方式。

**T-P1-06 交付说明**

- `audit.audit_log` 表追加式：应用账号对它只有 `SELECT / INSERT`，`UPDATE / DELETE` 已在授权脚本里 `REVOKE`。
- **自动留痕**：EF `SaveChanges` 拦截器记录实现 `IAuditedEntity` 的实体字段变更（动作 `entity.<实体>.updated`），与业务变更同事务落库——业务回滚，审计也回滚。
  只有 `User` / `Role` / `Tag` 这类低频、需要追溯的聚合实现该标记；作答流水不实现，否则考试高峰的写入量会被审计放大。
- **显式审计**：业务动作（建用户、改用户、重置密码、分配角色、建角色、改角色、名单导入）由 `IAuditRecorder` 记录，并带上操作人、IP、User-Agent。
- 接口：`GET /audit-logs`（按动作 / 目标类型 / 目标 ID / 操作人 / 时间范围过滤，分页），权限 `audit:read`。
- 授权脚本补上 `catalog` schema 的读写权限。

**T-P1-05 交付说明**

- 接口：`POST /users/import`（multipart，字段 `file`），权限 `user:import`。
- CSV 列名同时接受中文与英文（账号 / 姓名 / 学院 / 专业 / 班级 / 邮箱 / 角色 / 密码）；编码自动识别 UTF-8（含 BOM）、UTF-8、GB18030。
- **逐行处理**：单行出错只跳过该行并记录行号与原因，不阻断整批；列数不齐的行按缺列补空处理。
- **重复账号执行更新且不重置密码**——重复导入名单不该把学生的密码改掉。
- **自动创建组织维度标签**：缺失的院系 / 专业 / 班级按层级创建并挂接，编码自动去重。

- **题型配额与难度配额都给出时按比例交叉分配**，两个方向的合计都精确等于配额。
- **池量不足抛 `422 / 23101`**，逐条列出缺口（题型、难度、需求数、可用数、原因），**绝不降级补题**；缺口同时留痕在方案上。
- 分值分配复用 `ScoreAllocator`：分配结果之和精确等于目标总分；`by_difficulty` 模式按难度等级加权。
- 接口：`GET /papers/{id}/blueprint`、`PUT /papers/{id}/blueprint`、`POST /papers/{id}/blueprint/generate`、`GET /papers/{id}/blueprint/diff`。
- **错误响应带结构化载荷**：422 的响应体里直接带 `shortfalls`（组卷）与 `items`（发布校验），前端不用再发一次请求。
- 相对设计文档的偏差：`blueprint` 表增加 `generated_items`（jsonb）保存抽题结果——设计里的 `GeneratedItemIds` 没有对应列。

**T-P3-06 交付说明**

- 新增领域服务 `PaperVariantBuilder`：由已发布快照派生考生实际卷面。
  - 标准卷：题序与选项都不动，`variantKey = STD`。
  - 小梅花：题序不动，每题选项按 `hash(questionId, studentKey, sessionSeed)` 洗牌。
  - 大梅花：题型块顺序保留，块内题序洗牌，选项同小梅花。

**T-P5-03 交付说明**

- 接口：`POST /attempts/{id}/heartbeat`，返回服务端时间、剩余秒数、断连与警告计数、当前状态。
- **断连判定在服务端**：距上次心跳超过 `heartbeatTimeoutSeconds`（默认 45 秒）即算断连一次。
- **同一次断网只记一次**：判定后把心跳置空，因此每两秒检查一次的聚合推送不会把一次断网记成几十次。
- 断连次数超过 `maxDisconnect` 时按 `network_timeout` 自动交卷。
- 相对设计文档的偏差：`delivery.attempt` 增加 `last_heartbeat_at` 列——设计表里没有，但监考面板要显示「最近心跳时间」，没有它无法判断离线。

**T-P5-05 交付说明**

- 新增两个 Hub：`/hubs/proctoring`（监考教师订阅场次分组）与 `/hubs/exam`（考生订阅自己的作答会话）。
- **Redis Backplane**：多实例部署时靠 Redis 广播，客户端不必连到同一台机器；连接复用基础设施已注册的 Redis multiplexer。
- **连接鉴权双支持**：WebSocket 握手带不了 `Authorization` 头，约定用 `?access_token=` 传令牌；只有 `/hubs` 路径启用查询串令牌，其它接口不受影响。
- 分组约定：监考按场次分组（`exam:{sessionId}`），考生按作答会话分组（`attempt:{attemptId}`）。
- 权限：监考通道要求 `proctor:monitor`；考生通道校验只能订阅自己的作答会话。
- 功能测试用真实的 Redis 容器 + SignalR 客户端验证查询串令牌、分组路由与权限拒绝。

**T-P5-06 交付说明**

- 每条消息含每名考生的状态：作答状态、切屏 / 断连 / 警告计数、最近心跳时间、是否离线、已答题数与总题数。

- 接口：`GET /exam-sessions/{id}/monitoring` 拿监考初始快照（实时通道断线重连后也用它补齐数据）。

**T-P6-01 交付说明**

- 新增领域策略 `IScoringStrategy` 与五个实现：单选、判断、多选、简答、综合。
- **多选规则**：错选一律 0 分；只漏选按 `满分 × 命中数 / 正确项数 × 0.5`；全对满分；分数按 0.5 步进取整。
- **判断题比较原始选项键**（判断题固定两个选项，置换没有意义）。
- **关键词匹配先归一化**：全角转半角、去空白、去中英文标点、大小写折叠；要点关键词**全部命中**才算该要点得分（AND 语义）。
- 简答与综合题产出**建议分**（`AutoSuggested`），不是最终分；客观题自动定分（`AutoScored`）。
- 综合题按命中步骤分占比折算，评分明细带 ✓ / ○ 标记，供阅卷人核对。

**T-P6-02 交付说明**

- **交卷事务内完成判分**：客观题直接定分（`auto_scored`），主观题产出**建议分**（`auto_suggested`，状态 `suggested`），不是最终分。
- 判分只认**已发布的快照**：卷面上是什么就按什么判，题目后来改了也不影响这次判分。
- 接口：`GET /attempts/{id}/scores` 取回成绩汇总与逐题明细（命中项 / 漏选项 / 说明）。
- 交卷响应直接带成绩：客观分、客观满分、待阅标记、总分、总分上限与成绩可见性。
- 主观题未定分时成绩可见性为 `pending_review`（待阅），客观题定分后为 `objective_only`；成绩发布后的可见性在 T-P6-07 落地。

**T-P6-03 交付说明**

- 新增 `ReviewTask` 聚合（`grading.review_task`）：作答原文、系统建议分、本任务满分、状态、指派人、阅卷人、最终分与评语。
- **交卷时自动生成待阅任务**：主观题生成任务，客观题不生成（它们已经自动定分）。
- **综合题按步骤拆分**：一步一条任务，任务满分按卷面步骤分拆分，建议分按步骤分占比折算；阅卷人只判这一步。
- **完全没作答的题不生成任务**：得分就是 0，没有可阅的内容。
- 接口：`GET /review-tasks`（队列，可按状态 / 场次 / 只看我的过滤）、`GET /review-tasks/count`（待领取 / 阅卷中 / 已阅完 / 我的）。
- 队列项带 **第 N 次作答**（`attemptNo`）与考试名称，重考场景下能分清是哪一次。

**T-P6-04 交付说明**

- **领取是先到先得**：`POST /review-tasks/{id}/claim`。领域规则守「任务不在待领取状态就失败」，数据库的 xmin 令牌守「两人同时点领取只有一人成功」——后者拿 409，并发冲突由工作单元统一翻译成应用层异常。
- **指派只是分给他，不是替他领**：`POST /review-tasks/{id}/assign`。任务仍留在待领取队列里等人来领，且**只有被指派人能领**——指派不是摆设。
- 指派前校验对象：账号必须存在、未被禁用或锁定、且**拥有阅卷权限**，否则当场拒绝，不把卷子分给领不了的人。
- 接口：`GET /review-tasks/{id}`（卷宗详情：作答原文、参考答案、评分要点命中）、`GET /review-tasks/{id}/neighbors`（上一份 / 下一份）。
- **上一份 / 下一份按队列顺序**（创建时间、主键）找相邻任务，翻页之外还能按顺序跳着阅卷；过滤条件与队列一致。
- 队列过滤补齐接口契约：`examSessionId`、`questionId`、`status`、`assigneeId`、`mine`（只看指派给我的）。
- 领取与指派都进审计流水（`review_task.claim` / `review_task.assign`），记录阅卷人、指派人与操作人。
- 并发冲突在基础设施层翻译一次：上层只认得业务异常，EF 的原始消息不进响应体。

**T-P6-05 交付说明**

- **评分端点**：`POST /review-tasks/{id}/grade`，请求体 `{ "score": 7.5, "comment": "要点 1、2 覆盖到位" }`，返回任务状态、最终分、满分、评分结果状态与**这是第几次改动**（`revision`）。
- **分数校验 0..满分、步进 0.5**：满分是任务上的数，只有领域层知道，所以分数一律由领域规则拒绝（422），前端只需要认一种错误；负分、超满分、步进不对都是同一种响应形状。
- **直接给待领取的卷子评分等于先领再评**：阅卷人从队列里点开就能判，不必先点一次领取。
- **别人正在阅的卷子不能抢**（422）；**已阅完的卷子允许改分**——改分不是被禁止的事，是被记录的事。
- **综合题按步骤评分**：一步评完只更新整题总分，**全部步骤评完才定分**（`scoreResultStatus` 由 `suggested` 转 `final`）；期间成绩仍是「待阅」。
- **改分流水 `app.grade_revision` 追加式**：只有 INSERT / SELECT，应用账号对它没有 UPDATE / DELETE 权限（与答案流水同款约束）。每评一次留一条：改前多少分、改后多少分、谁改的、什么时候改的、评语是什么。
- **学生端可见**：`GET /attempts/{id}/grade-revisions` 返回这次作答的全部改分记录（本人可见；教师凭 `attempt:read:all` 也能看）。别人看不到自己的成绩，也看不到别人的改分记录。
- 评分进审计流水（`review_task.grade`），记录改前分、改后分与阅卷人；评分结果字段变更由 EF 拦截器自动记入审计。

**T-P6-06 交付说明**

- **批量端点**：`POST /review-tasks/batch-adopt`（权限 `review:batch-adopt`）。两种范围：点名任务（`taskIds`）或按场次批量（`examSessionId`，可再用 `questionId` 收窄）；两个都不给直接拒。
- **二次确认是接口的一部分**：请求必须带 `confirm: true`，否则拒绝。批量定分不可逆，客户端先弹确认框，服务端也要看到确认的意思。
- **只影响 `pending` 任务**：已经领走、阅完、或者指派给了别人的卷子照旧不动，逐条说明为什么跳过；点名的任务里有找不到的，也逐条报出来。
- **逐条结果**：每条给出「采纳 / 跳过」、最终分与跳过原因，外加总数、采纳数、跳过数——前端不用猜哪几份没生效。
- **单次上限**：`maxCount`（默认 200，硬上限 500），超量直接拒绝并提示分批，不做静默截断。
- **批量采纳同样留痕**：每道题一条改分流水（学生端可见），审计记 `review_task.batch_adopt`（总数 / 采纳数 / 跳过数 / 操作人）。
- **综合题按步骤采纳**：一步采纳只更新整题总分，全部步骤采纳完才定分——和单份评分是同一套规则。

**T-P6-07 交付说明**

- **发布端点**：`POST /exam-sessions/{id}/publish-grades`（权限 `grade:publish`），范围两种：`all`（全部成绩）与 `objective_only`（只发布客观题）。
- **发布记录**（`grading.grade_publication`）：场次、范围、发布人、发布时间，以及**这次发布覆盖的作答快照**。快照式是有意的：发布之后才交卷的人不会被顺带放出去；晚交的人要单独再发一次。
- **可见性由服务端说了算**：成绩没发布之前，学生只看得到客观题分与「待阅」——**主观题的得分、命中项、漏选项全部扣住**（要点命中等于把答案抖出来）；发布之后才给完整成绩。
- **总分随发布而变**：发布前总分只算客观题那部分，发布后才变成完整总分。这不是算错，是「还没放出来」。
- **改分流水同样扣住**：成绩没发布之前，`GET /attempts/{id}/grade-revisions` 对学生是空的——流水里全是分数。
- **教师视角不受影响**：`GET /exam-sessions/{id}/grades`（权限 `analytics:read`）列出整场考试的成绩、逐人总分、待阅标记与发布状态，教师看得到全部。
- **发布的边界**：场次还没发布不能发成绩；一场考试没人交卷也不能发（没成绩可发）；点名发布时，作答必须属于这场考试。
- 发布进审计流水（`exam_session.publish_grades`），记录范围、发布人与覆盖的作答数。

**T-P6-08 交付说明**

- **报告端点**：`GET /attempts/{id}/report`——逐题给出自己的作答、得分、满分，以及（到公布时机才给的）正确答案、参考答案与解析。另加 `GET /my/results`：我的成绩列表。
- **答案公布三档策略**：`immediately`（开考即公布）、`after_submit`（本人交卷后）、`after_close`（场次关闭后）。没到公布时机，报告里的正确答案、参考答案、解析**一律不给**（字段给空，不是给个假的）。
- **策略在发布时冻结进快照**（`paper_snapshot.answer_policy`）：考完之后改试卷，改不动这场考试什么时候公布答案；内容哈希也算上策略。
- **考试进行中答题接口永不返回答案**：`GET /attempts/{id}` 的卷面里没有正确选项、没有解析、没有参考答案——这条有专门的测试盯着。
- **成绩可见性与答案公布是两件事**：分数看发布（发布前扣住主观题的分），答案看公布策略（到时机才给）。报告里两项各管各的。
- 报告只给本人看；教师要看全场的成绩，走场次成绩列表。

### T-P7-01 错题回流
- **依赖**：T-P6-02、T-P6-05
- **产出**：`ScoreFinalized` 事件 → 错题写入、错误次数累计、错因分类。
- **验收**：练习与考试中的错题都回流；主观题部分得分也回流。

**T-P7-01 交付说明**

- **先有出站箱**：新增 `outbox.outbox_message` 与 `OutboxSaveChangesInterceptor`——领域事件与聚合状态落在**同一个事务**里，不会出现「状态改了、事件丢了」的半截状态。`Exam.Worker` 轮询未派发的消息，派给进程内处理器（本期没有外部消息队列）。
- **`ScoreFinalized` 事件**：客观题交卷即定分、主观题人工评分后定分，两者都发事件；只有建议分（还没定分）不发。
- **错题回流**（`learning.mistake`）：主观题最终分不满分、客观题判为错误，都进错题本；**主观题拿部分分也算错**（要点没覆盖到）。
- **错因分类**：多选漏选 / 多选错选 / 单选错选 / 判断结论错 / 简答要点未覆盖 / 综合题步骤缺失 / 未作答。
- **同一次作答里改分不累计次数**：教师复核后改分只更新错因；再错一次（新的作答）才累计次数。
- **后来答对就移出**：下一次作答答对了，这道题不再是错题。
- 练习与考试的错题都回流（来源记在 `source_type`）。
- **功能测试主机要跟生产装配一致**：`ExamWebFactory` 自己注册 DbContext，拦截器少接一个，事件就落不了库——这类偏差要当心。

### T-P7-02 错题本与单题重做
- **依赖**：T-P7-01
- **产出**：错题本查询与过滤、单题重做、答对后移出。
- **验收**：错题可按标签/题型/时间过滤；重做正确后错题本不再显示。

**T-P7-02 交付说明**

- **错题本**：`GET /api/v1/mistakes`——可按标签（连标签子树）、题型、时间范围过滤，带分页。条目带题目信息（题号、题型、题干、标签名）、错因、错次、来源与最近做错的时间，前端拿到就能直接显示。
- **已掌握的默认不显示**：要看得显式要 `includeResolved=true`。
- **标记已掌握**：`POST /api/v1/mistakes/{questionId}/resolve`。
- **单题重做**：`POST /api/v1/mistakes/{questionId}/redo`——把这道题做成一份**只有一道题的练习**（新试卷 + 快照 + 练习开放单），并直接开好会话，返回练习单与作答会话 ID。
- **重做答对之后错题就出本**：重做走的是正常的作答与交卷流程，对答案定分即回流，错题随即被移出。
- **练习也有卷面**：`AttemptPaperResolver` 统一解析卷面来源——考试走场次绑定的快照，练习走练习开放单挂的试卷；保存答案、交卷、查看会话三条路径都认这两种来源。

### T-P7-03 能力画像
- **依赖**：T-P7-01
- **产出**：`AbilityProfile` 增量更新、掌握度算法、样本不足标注。
- **验收**：样本量 < 5 时标注"样本不足"且不参与排序。

**T-P7-03 交付说明**

- **能力画像**（`learning.ability_profile`）：某学生在一项**能力维度标签**上的掌握情况——掌握度、样本量、完全正确的题数。知识点标签不进画像。
- **掌握度算法**（`MasteryCalculator`，领域服务）：`mastery =（Σ 得分率² 的加权平均）/（1 + 0.1 × ln(1 + 样本量))`。得分率先平方再按题目分值加权平均——高分被放大、低分被压低，区分度比直接平均更明显。
- **样本只认已定分**：客观题自动定分与主观题人工定分算数，建议分（还没定分）不算。
- **样本不足不参与排序**：样本量少于 5 标「样本不足」，排在排序的后面，另给 `insufficientCount`。
- **接口**：`GET /api/v1/abilities/profile`——返回能力标签、掌握度、样本量、完全正确数、样本是否充足与中文档位（掌握 / 熟悉 / 薄弱 / 样本不足）。
- 画像由 `ScoreFinalized` 事件驱动更新，与错题回流同一条事件。

### T-P7-04 统计读模型
- **依赖**：T-P6-02
- **产出**：`exam_statistic` / `question_statistic` / `type_statistic` 增量更新 + 每日全量重算。
- **验收**：统计与原始作答数据一致（抽样核对）。

**T-P7-04 交付说明**

- **读模型落在 `analytics` schema**：`exam_statistic`（场次级）、`question_statistic`（逐题）、`type_statistic`（题型）三张表。它们是**派生数据**——由原始作答数据重算得出，不承载业务规则，因此不软删除、不进审计流水；错了靠重算纠正。
- **口径写在领域层**（`AnalyticsRules`）：及格优先用**试卷设置的及格分**（没设才按 60% 得分率兜底），优秀按 85% 得分率，分数段按得分率分档（90 分以上 / 80–90 / 70–80 / 60–70 / 60 分以下）。同一套阈值对 40 分卷与 100 分卷同样成立，统计口径与学生看到的及格分不会打架。
- **统计对象是已交卷的作答**：重考按「最后一次」取一份（试卷设了「重考取最好」就取分数最高的一次）。应考人数 = 名单上的考生 ∪ 进过考场的考生，缺考 = 应考 − 交卷。
- **逐题与题型只算真正作答的人次**：空白答案不进分母——没作答的人不该拉低这道题的平均分。「答对」= 拿到这道题的满分。
- **两层刷新**：查询时发现读模型落后于原始数据（拿读模型的 `updated_at` 与作答、评分的最近一次变更时间比）就当场重算，保证**统计与原始作答数据始终一致**；`Exam.Worker` 另有定时作业——每隔几分钟增量重算落后的场次，每天一次全量重算修正增量误差。
- **重算是整体替换**：先删这场考试的旧行再写新行，不留半新半旧的数据；同一场考试的重算用事务 + 咨询锁串行执行，并发重算不会互相踩。
- **接口**：`GET /api/v1/statistics/exam-sessions/{id}`（`analytics:read`）——平均分、极差、及格率、优秀率、分数段分布、题型得分率与逐题统计（题号、题型、满分、作答应数、正确数、正确率、平均分、掌握度）。逐人成绩明细与讲评建议随 T-P7-05 一起提供。
- **功能测试抽样核对**：两名考生交卷后逐项核对平均分、极差、及格率、优秀率、分数段、题型得分率与逐题统计，并核对读模型三张表的行数；改分之后统计跟着更新。

### T-P7-05 管理端成绩分析
- **依赖**：T-P7-04
- **产出**：平均分/极差/及格率/优秀率、分数段分布、题型得分率、逐题正确率与讲评建议。
- **验收**：**全部基于真实作答数据**，无模拟数据；低于阈值给讲评建议。

**T-P7-05 交付说明**

- **场次成绩分析**（`GET /api/v1/statistics/exam-sessions/{id}`，`analytics:read`）：平均分、极差、及格率、优秀率、分数段分布、题型得分率、逐题统计（T-P7-04 的读模型），外加本期的**逐人成绩明细**与**逐题讲评建议**。
- **逐人成绩明细**（`roster`）：每位考生的客观分、主观分、总分、总满分与得分率，按总分从高到低排。取卷规则与场次统计一致——重考按最后一次（或「重考取最好」的最高分）取一份。
- **讲评建议**（`suggestion`）：正确率或得分率低于 60% 就提示「建议安排讲评」；正确率良好则说明无需专门讲评；**没人作答的题不给建议**——没有数据可依据。建议文案由领域规则 `AnalyticsRules.ReviewSuggestion` 统一产出，前后端不会各说各话。
- **逐题正确率**（`GET /api/v1/statistics/questions/{questionId}`，`analytics:read`）：一道题在**全部场次**里的总体正确率、掌握度、讲评建议，以及逐场次明细（每场答了多少、正确率多少）。跨场次汇总用读模型里的**总得分**而不是四舍五入后的平均分，汇总值与原始作答数据一致。
- **逐题统计带题干**：前端要显示题号、题型与题干，读模型只存计数，题干与题号从卷面快照取，接口一次给全，前端不用再发第二个请求。
- **全部基于真实作答数据**：没有任何模拟数据或兜底假数；读模型落后于原始作答数据时先重算再出数。
- **功能测试**：逐人成绩明细、跨场次逐题正确率与讲评建议逐项核对。

### T-P8-01 练习开放单与可见性
- **依赖**：T-P3-01、T-P1-04
- **产出**：`PracticeAssignment` 聚合、组织标签范围、可见性判定。
- **验收**：不在范围内的学生看不到练习。

**T-P8-01 交付说明**

- **练习开放单**（`learning.practice_assignment`）：挂一份练习试卷、一组开放范围（组织标签）、开放期与上下架状态。单题重做走的就是这张单子——一份只有一道题的试卷就是一份练习。
- **可见性判定**（`PracticeVisibilityResolver`）：三个条件同时成立才看得见——**已上架**、**在开放期内**、**命中开放范围**。开放范围是组织标签，命中「标签本身或它的子标签」都算数；**范围为空表示全员可见**。
- **范围外就是没有**：不在范围内的学生，列表里不出现，详情接口也返回 404——不给「存在但无权」的信号。
- **接口**：
  - `GET /api/v1/practices`——可见练习列表，可按标题关键词与标签过滤（标签按练习对应试卷的标签算，父标签连子标签一起算），带分页。
  - `GET /api/v1/practices/{id}`——练习详情：题量、总分、标签、规则（可提交次数、反馈时机、错题回流、建议时长）与**自己还能做几次**。
- **规则以试卷上的练习规则为准**（`Paper.PracticeRules`）：开放单上的 `rules` 字段留给将来做单次覆盖。
- **功能测试**：班上学生能看到限定范围的练习，范围外的学生看不到也拿不到详情；全员可见的练习两边都能看到。

### T-P8-02 练习规则执行
- **依赖**：T-P8-01、T-P4-03
- **产出**：次数限制、反馈时机（即时/提交后）、错题回流开关、**不计时不强制交卷不限制切屏**。
- **验收**：次数用尽拒绝提交并提示；练习会话无 `deadlineAt` 强制。

**T-P8-02 交付说明**

- **练习也能开考**：`POST /api/v1/attempts` 现在认 `practiceAssignmentId`——练习单不在该生可见范围内时返回 404；考试场次与练习只能二选一。
- **练习不计时**：`Attempt.IsTimed` 区分考试与练习。练习会话的 `deadlineAt` 只是一个兜底值，**不会被强制交卷**，响应里 `timed` 为 `false`，前端据此不显示倒计时。交卷原因也只看考试：练习永远不会因为超时被记成 `time_up`。
- **练习不限制切屏**：焦点事件在练习下没有场次规则，不计上限、不警告、更不会强制交卷。
- **次数限制**（`maxAttempts`）：次数用尽就**不再给开新会话**，并提示「练习次数已用完（最多 N 次）」；交卷时也再挡一次——次数上限被调低之后，已经开出的会话不算数。
- **反馈时机**（`feedbackTiming`）：新增 `POST /api/v1/attempts/{id}/feedback`。
  - `immediate`：边做边看对错、正确答案与解析；
  - `after_submit`：交卷前调用返回 422，交卷后才给；
  - **考试不给反馈**——考试进行中泄露答案等于没有考试。
  - 反馈是**预览式判分**：不落库、不产生评分记录，因此不会误触发错题回流。
- **错题回流开关**（`reflowMistakes`）：关掉之后，练习里做错的题不进错题本。
- **规则来源**：练习规则以**练习试卷上的 `PracticeRules`** 为准，开放单上的 `rules` 字段留给将来做单次覆盖。
- **功能测试**：不计时不强制交卷、次数用尽拒绝开新会话、即时反馈、提交后才反馈、关掉错题回流五项逐条锁定。

### T-P8-03 学生端练习页面
- **依赖**：T-P8-02
- **产出**：练习中心（搜索 + 标签筛选）、练习作答页、即时反馈块、逐题解析、重新练习。
- **验收**：即时反馈模式下作答后立即显示对错与解析；"用时"真实统计。

**T-P8-03 交付说明**

- **练习中心**：`GET /api/v1/practices`（T-P8-01）——搜索按标题、标签筛选按练习对应试卷的标签，条目直接带题量、总分、标签、规则与自己还能做几次，前端不用再发第二个请求。

- **重新练习**：练习次数没用完时可以直接再开一次，序号接着排（`attemptNo` 递增）；次数与剩余次数在练习列表里就写着，前端不用自己算。
- **我的成绩**：练习的成绩也进「我的成绩」列表，带练习开放单的标题，不再是一片空白。
- **功能测试**：练习交卷后报告逐题给答案与解析、用时真实统计、次数没用完能再开一次。

### T-P9-02 压测与零丢答对账
- **依赖**：T-P4-04、T-P4-09
- **产出**：k6 脚本四场景、阈值断言、端到端对账脚本、`AnswerReconciliationJob`。
- **验收**：1000 VU 下错误率 < 0.1%、p95 < 500 ms、**丢答率 = 0**；对账作业在生产每日执行并告警。

**T-P9-02 交付说明**

- **k6 四场景**（`backend/tests/Exam.LoadTests/`）：`login`（认证链路）、`start-exam`（开考突发）、`answer-submit`（持续作答，每 8 秒一批）、`submit-burst`（交卷突发）。公共配置在 `common.js`。

### T-P9-03 性能调优与容量验证
- **依赖**：T-P9-02
- **产出**：EF 变更追踪规避、连接池与 PgBouncer 参数调优、Redis 缓存预热、索引评审。
- **验收**：压测指标达标或记录偏差原因与后续计划。

**T-P9-03 交付说明**

- **试卷快照缓存**（`PaperSnapshotCache`）：快照**发布后不可变**，既然不变就不必每次回库读。开考瞬间 1000 人同时进考场，读的是同一份快照——缓存住之后数据库几乎不承压。
  - 缓存的是**脱离跟踪的只读实例**：快照没有修改入口，缓存副本不会被变更跟踪器拖住、也不会跨作用域串味。
  - 用**进程内缓存**而不是 Redis：快照是不可变的大对象，序列化再反序列化的 CPU 代价高于回库一次，省下来的连接与 I/O 才是瓶颈。
- **只读查询不进变更跟踪**：错题本列表、成绩列表、作答列表、题目批量取用 `AsNoTracking`——这些路径只读不写，挂在变更跟踪器上纯属浪费内存。
- **连接池调优**：连接串显式带上 `Maximum Pool Size` / `Minimum Pool Size` / `Timeout` / `Command Timeout` / `Keepalive`，由 `DB_MAX_POOL_SIZE`（默认 80）、`DB_MIN_POOL_SIZE`（默认 10）、`DB_WORKER_MAX_POOL_SIZE`（默认 20）注入。
  - 直连 PG 时按「实例数 × 池大小 ≤ `max_connections=200`」算；启用 PgBouncer 后客户端池可以放大（事务池复用后端连接）。
  - 迁移作业直连 PG 且池大小压到 5——迁移不是业务流量。
- **索引评审**：逐条核对了高频路径的索引——作答按 `(attempt_id, question_id)` 唯一、评分结果按 `attempt_id`、答案按 `(attempt_id, question_id)` 唯一、错题按 `(user_id, wrong_count)`、答案修订按 `(attempt_id, client_seq, question_id)`，均已覆盖。
  - **补一条**：对账作业按交卷时间回看，加了部分索引 `ix_attempt_submitted`（只索引已交卷且未删除的行）——未交卷的会话不占索引空间。
- **偏差与后续**：压测指标需在同构压测环境实测（见 T-P9-02 的场景与阈值）；本轮先把结构性瓶颈（快照重复读、只读查询跟踪、连接池无上限）去掉。容量结论以压测报告为准。

### T-P9-06 监控与告警完善
- **依赖**：T-P9-02
- **产出**：完整 Grafana 看板（作答链路、监考、容量）、告警规则与路由、值班手册。
- **验收**：人为制造异常能触发预期告警。

**T-P9-06 交付说明**

- **先说结论**：上一轮的告警规则**一条都触发不了**。不是配置写错，是指标对不上——
  规则引用的指标应用根本没导出，或者导出了但从来没被赋值。本轮把这件事从根上修掉，
  并加了 CI 闸门防止复发。
- **查出并修掉的六类缺陷**：
  1. `attempt_active_sessions` 从来没被 +1（`AttemptStarted` 根本没人调用），
     `AttemptFinished` 还在给练习作答减数（练习没有场次 ID）。
     → 改为 Worker 从 `delivery.attempt` 采样，按**心跳新鲜度**判定；场次不在进行中时序列自动撤掉；
     进程内的加减法删除。多实例与重启后进程内计数必然失真，心跳一停才能立刻看出掉线。
  2. 规则写的是 `http_server_requests_total{status=...}`，prometheus-net 实际导出的是
     `http_requests_received_total{code=...}`。→ 自己写了 `HttpMetricsMiddleware`，
     导出 `http_requests_total{method,route,status}`；route 取路由模板不取原始路径
     （原始路径由客户端控制，拿它当标签等于把标签基数交给攻击者）。
  3. `ExamDatabaseConnectionsExhausted` 依赖 `npgsql_connections_closed_total` 与 `db_pool_*`——
     **Npgsql 没有公开的连接池统计接口**（Npgsql 10.0.3 的 XML 文档里 "Statistics" 零命中）。
     → 改用 `pg_stat_activity` + `max_connections`，已实测 `exam_app` 账号都读得到。
  4. 设计文档 §5.1 承诺的 `clock_offset_ms`、`redis_command_duration_seconds{op}`、
     `signalr_connections`、`exam_sessions_published` **一个都没实现**；§5.4 列的
     「时钟偏移」「Redis 不可用」「备份失败」三条告警**没有任何指标支撑**。
     → 全部补齐：时钟偏移探针（应用时钟对数据库时钟）、Redis 探针 + 各命令耗时、
     SignalR 连接计数、备份任务把状态写成 textfile 指标由 node_exporter 采集。
  5. `attempt_answers_saved_total{result}` 把「单题被拒」和「整批」混在一个计数器里，
     错误率的分母被悄悄改小。→ 拆成批次口径（saved/duplicate/rejected）
     与单题口径 `attempt_answer_items_rejected_total`。
  6. 延迟直方图带 `result` 标签，被拒批次的 0 秒混进去，p95 被拉低、掩盖真实延迟。
     → 直方图不带标签，只观测真正落库的批次。
- **指标按进程隔离**：API 侧与 Worker 侧拆成两个接口、两个实现、两个注册表，
  `IExamMetrics` 只在 API 进程解析、`IWorkerMetrics` 只在 Worker 进程解析。
  同一个指标名被两个进程各报一次，告警里的比例就翻倍——这比「指标不存在」更隐蔽。
  `MetricRegistryTests` 断言两套注册表互不污染。
- **告警规则 16 条**：覆盖设计文档 §5.4 的全部条目，另加切屏激增、HTTP 5xx、

- **实测结论**（真实后端）：答错的题进错题本（`wrongCount`、`reasonLabel`、`sourceTypeLabel` 都有）；
  单题重做返回 `practiceAssignmentId` 与 `attemptId`；
  工作台返回待完成练习、进行中考试、学期平均分、待订正错题、推荐练习、最近成绩、
  成绩趋势与错题分布。
- **要注意的**：错题回流是**异步**的（`ScoreFinalized` 事件走 outbox，由 worker 落本）——
  交卷后立刻看错题本可能还没这一条，过一拍才有。
